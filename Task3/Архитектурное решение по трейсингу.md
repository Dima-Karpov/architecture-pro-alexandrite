### Функциональные требования

Сквозной след заказа на critical path (без смены бизнес-логики Shop / CRM / MES). Use case’ы — из [Task1](../Task1/Планирование%20анализ%20идентификация%20проблем%20и%20поиск%20решений.md). Метрики/алерты очередей уже в [Task2](../Task2/Выбор%20и%20настройка%20мониторинга%20в%20системе.md) — трейсинг отвечает на «где именно завис заказ».

| **№** | **Действующие лица или системы** | **Use Case** | **Что покрываем трейсом** |
| :---: | :--- | :--- | :--- |
| UC3 | API user, MES API, RabbitMQ, CRM API | Партнёрский заказ через API | HTTP partner → publish → consume CRM; `order_id` на всём пути |
| UC4 | MES API, S3, очередь расчёта | Расчёт цены → PRICE_CALCULATED | publish/consume calc-очереди + смена статуса (не один HTTP-span на 2–30 мин) |
| UC6 | CRM API ↔ RabbitMQ ↔ MES API | Смена статусов | publish/consume CRM↔MES + `order.status` в атрибутах spans |

### Нефункциональные требования

| **№** | **Требование** |
| :---: | :--- |
| O2 | Сквозной след Shop→CRM→MES→очередь: `trace_id` + `order_id`; без PII в cleartext ([Task1](../Task1/Планирование%20анализ%20идентификация%20проблем%20и%20поиск%20решений.md)). |
| T1 | По `order_id` в Jaeger видно, на каком hop завис заказ (HTTP или messaging), а не только «очередь выросла» (Task2). |
| T2 | Propagation: W3C Trace Context в HTTP и те же заголовки в AMQP headers — иначе асинхронный путь рвёт след. |
| T3 | OTLP → OpenTelemetry Collector → Jaeger; head-based sampling ~10% + always-on errors/critical routes. Демо 3.1 — 100%. |
| T4 | Jaeger UI / query — только внутренняя сеть (VPN/SSO); scrub PII в collector; без публичного ingress. |
| T5 | Хранилище трейсов — persistent + retention **7–14 дней** (демо 3.1 — in-memory). `order_id` — span attribute **и** явный AMQP header (не только baggage). |

### Решение

#### 1. Анализ C4 / точки поломки

Трейсинг — инициатива **3** (P1) из Task1: закрывает O2 и дополняет мониторинг Task2. Новые контейнеры на to-be уже заложены: **OpenTelemetry Collector** + **Jaeger**. Здесь фиксируем, *какие hops* инструментируем и *где* рвётся след без propagation.

Схемы Task3 (новое **красным**; автоалертинг по spans — **зелёным**):

- Трейсинг: [`c4/01-tracing.puml`](c4/01-tracing.puml) · [`c4/01-tracing.svg`](c4/01-tracing.svg)
- Алертинг по трейсам: [`c4/02-tracing-alerting.puml`](c4/02-tracing-alerting.puml) · [`c4/02-tracing-alerting.svg`](c4/02-tracing-alerting.svg)

Контекст as-is / to-be (6 мес): [`Task1/c4/01-containers-as-is`](../Task1/c4/01-containers-as-is.puml) · [`Task1/c4/02-containers-to-be-6m`](../Task1/c4/02-containers-to-be-6m.puml).

| Слой C4                                     | Трейсим? | Зачем / почему нет                                                 |
| ------------------------------------------- | :------: | ------------------------------------------------------------------ |
| Shop API, CRM API, MES API                  |    да    | HTTP entry + исходящие вызовы на critical path заказа              |
| RabbitMQ publish / consume (CRM↔MES + calc) |    да    | Большинство «заказ завис» — между сервисами, не внутри одного HTTP |
| Outbox relay → publish                      |    да    | Span relay + `order_id` связывает commit в БД с уходом в брокер    |
| DLQ / parking-lot consume                   |    да    | Error-span + причина — triage без письма партнёра                  |
| Internet Shop UI / MES UI / CRM UI          |   нет    | RUM вне scope; кейс — API/очередь, не клики                        |
| PostgreSQL / S3 internals                   |   нет    | Дорого и шумно; достаточно знать hop «перед/после» БД/S3           |

**Точки зависания** (куда смотрит Support по `order_id`):

| Симптом | Где рвётся / залипает | Что видно в трейсе |
| --- | --- | --- |
| Партнёр: «заказ не получен» | partner HTTP → MES publish → CRM consumer | Последний span до дыры; error на consume / уход в DLQ |
| Статус в CRM есть, в MES нет (или наоборот) | CRM↔MES publish/consume | Messaging span без child consume / error на consumer |
| Долго до PRICE_CALCULATED | очередь расчёта | Age в метриках (Task2) + span publish calc без consume / долгий worker-span |
| «В БД есть, в Rabbit нет» | Outbox lag | Span outbox relay отстаёт / отсутствует publish |
| Ядовитое сообщение | DLQ | Error-span + queue=dlq; корреляция по `order_id` |

#### 2. Данные в трейсе

Минимальный набор атрибутов — хватает для triage, без PII и без payload 3D-модели.

| Поле / атрибут | Где | Зачем |
| --- | --- | --- |
| `trace_id` / `span_id` | все spans | Склейка цепочки; ссылка из логов (Task4) |
| `service.name` | resource | Shop / CRM / MES / calc-worker |
| HTTP `route`, `method`, status | server/client spans | RED-контекст одного hop |
| Messaging: `messaging.destination` (queue), `messaging.operation` (publish/receive) | AMQP spans | Видно, *какая* очередь и publish vs consume |
| **`order_id`** | span attribute на critical spans **+** AMQP app-header `order_id` рядом с `traceparent` | Поиск в Jaeger; consumer восстанавливает id даже если baggage срезали |
| **`order.status`** (до/после, где известно) | смена статуса / calc | Понять, на каком статусе остановились |
| duration | каждый span | Кто тормозит |
| error / exception type (без stack с PII) | failed spans | Быстрый фильтр битых hops |

**Носитель `order_id`:** канон — **span attribute + явный AMQP/HTTP header**. W3C Baggage не единственный канал: через брокер/прокси часто теряется или раздувает заголовки.

**Не кладём в span attributes:** ФИО, телефон, email, адрес, тело 3D / URL объекта S3 с токенами, полный AMQP payload.

#### 3. Мотивация

Task2 отвечает: *что-то плохо с очередью/API*. Трейсинг отвечает: *на каком hop этот `order_id`*. Без следа MTTD по жалобе партнёра остаётся «письмом менеджеру», а разбор — ручным grep по трём сервисам.

| Боль | Без трейсинга | С трейсингом |
| --- | --- | --- |
| «Где завис заказ?» | Метрики depth/age + догадки по логам трёх API | Один `order_id` → цепочка spans до обрыва |
| Partner churn | Узнаём от менеджера партнёра | Error-span / DLQ + тот же `trace_id` в логах → triage до churn |
| Calc 2–30 мин | Кажется «MES тупит» целиком | Отдельные publish/consume + статус; не путаем с HTTP 5xx |

**Метрики влияния** (продукт / ops, не Prometheus-ряды):

| Метрика влияния | Ожидание |
| --- | --- |
| MTTD «заказ завис» (до жалобы) | Падает: алерт Task2 + переход в Jaeger по `order_id` за минуты |
| % инцидентов «заказ не дошёл», закрытых без жалобы партнёра | Растёт за счёт DLQ/error-span triage |
| Time-to-locate (от алерта до виновного span) | Минуты вместо часов ручного сбора логов |
| Доля broken traces на critical path (нет consume после publish) | Сигнал качества instrumentation / propagation |
| Churn партнёров по причине «заказ потеряли» | Снижение как бизнес-итог надёжности + observability |

#### 4. Предлагаемое решение

Стек (не «прямой Jaeger Thrift из урока» — без единой точки семплинга и redaction):

| Элемент | Выбор | Почему |
| --- | --- | --- |
| SDK | OpenTelemetry в Shop/CRM (Java / Spring) и MES (C#) | Один vendor-neutral API; уже на to-be Task1 |
| Экспорт | **OTLP → OpenTelemetry Collector → Jaeger** | Семплинг, scrub/redaction, смена бэкенда без правки приложений; Thrift «напрямую в Jaeger» — хрупко и без процессоров |
| Propagation | W3C Trace Context (`traceparent` / `tracestate`) в HTTP | Стандарт OTel; совместим с Gateway |
| Async | W3C в **AMQP headers** + **`order_id` header**; consumer → continue trace + span attr | Без W3C — дыры в следе; без `order_id` header — нельзя найти заказ после брокерного hop |
| Sampling | Head-based **~10%** + always-on на errors и critical routes (partner, status sync, calc) | Баланс стоимость / видимость |
| Jaeger storage / retention | Persistent backend + **retention 7–14 дней** (в демо 3.1 — memory, `jaeger-instance.yaml`) | Без TTL диск/индекс растут; 7–14 дней хватает для triage жалоб по заказам |
| Демо 3.1 | Minikube + Jaeger all-in-one, sampling **100%**, два сервиса | Доказательство пайплайна OTLP + propagation |

Красное на C4 ([`c4/01-tracing`](c4/01-tracing.puml)): OTel SDK в API, Collector, Jaeger, связи OTLP и propagation (HTTP + AMQP).

**Демо 3.1** (файлы в `Task3/`): `service-a` → `service-b` по HTTP с propagation, экспорт OTLP в Jaeger; runbook — [`README.md`](README.md); скрин — `jaeger-trace.png`.

#### 5. Дополнительно: автомониторинг / алертинг по трейсам (зелёное)

Метрики Task2 — источник **P0** по очередям (depth / age / DLQ). Из трейсов алертим только то, что Collector реально умеет посчитать — не «магию по дереву spans в Jaeger».

**Пайплайн:** OTLP → Collector (**spanmetrics** connector: latency / error rate по `service.name` + route / messaging.destination) → Prometheus → Alertmanager (тот же, что Task2). После алерта Support идёт в Jaeger по `order_id` / `trace_id`.

| Сигнал | Откуда берётся | Смысл | Связь с Task2 |
| --- | --- | --- | --- |
| Error rate / p99 на partner HTTP и messaging hops | spanmetrics из spans | Отказ create/publish/consume на critical path | Дополняет 5xx / DLQ |
| Stuck calc / «заказ завис по статусу» | **не** из дерева spans напрямую | Age очереди calc + DLQ (Task2) = P0; трейс — drill-down «какой hop» | Primary = Task2; Jaeger уточняет |
| Broken trace rate (publish без child consume) — later | отдельный job / recording по sampled traces | Качество instrumentation / propagation | Не P0; сигнал зрелости |

Схема: [`c4/02-tracing-alerting`](c4/02-tracing-alerting.puml). Без зелёного контура трейсинг — «смотрелка»; с spanmetrics — мост к Alertmanager из Task2 без второго алерт-стека.

#### 6. Компромиссы

| Что сознательно не делаем / ограничиваем   | Почему принимаем                                                                    |
| ------------------------------------------ | ----------------------------------------------------------------------------------- |
| UI без RUM / browser tracing               | Кейс — API и очередь; RUM не закрывает partner/CRM consumer                         |
| Нет детальных spans внутри PostgreSQL / S3 | Шум + стоимость; hop «API↔DB/S3» достаточно по ошибке/latency родителя              |
| Calc 2–30 мин ≠ один HTTP-span             | Иначе «вечный» span и ложные таймауты; только publish/consume + `order_id` / статус |
| 100% sampling только в демо / staging      | Иначе дорого по CPU/сети/хранилищу Jaeger                                           |
| Не полный service mesh tracing             | Yagni: трёх приложений + Rabbit хватает с SDK                                       |
| Baggage как единственный носитель `order_id` | Через AMQP/прокси нестабильно; канон — attribute + явный header                     |
| Отдельный «order journey» store / SLA только из spans | Yagni: P0 age/DLQ из Task2; spans → spanmetrics + drill-down в Jaeger               |
| Retention > 14 дней без отдельного cold tier | Дорого; жалобы партнёров разбираем в окне 1–2 недель                                |

#### 7. Безопасность

| Контроль | Как |
| --- | --- |
| Доступ к Jaeger UI / query | Только VPN (или аналог) + SSO; роли Support / DevOps |
| Collector | Во внутренней сети; приложения шлют OTLP внутрь, не наружу |
| Публичный ingress на query | Нет |
| PII / секреты | Attribute processor в Collector: drop/scrub email, phone, raw payload; запрет логировать body 3D |
| Корреляция | `order_id` + `trace_id` — достаточно для triage без персональных данных |

#### 8. Демо 3.1

Minikube + Go-сервисы доказывают пайплайн OTLP→Jaeger и propagation HTTP. Целевое решение выше (Collector, AMQP headers, sampling, retention); k8s-файлы — иллюстрация пайплайна, не замена EC2-контура на 6 месяцев (Task1 S1).

### Альтернативы

| Вариант | Почему не берём |
| --- | --- |
| Прямой Jaeger Thrift / Jaeger client из урока | Нет единой точки семплинга и redaction; Collector уже на to-be Task1 |
| Zipkin как основной бэкенд | Дублирует Jaeger-контур курса/to-be; миграция без выигрыша для кейса |
| Datadog / коммерческий APM all-in-one | Vendor lock и стоимость; стек Task1/2 уже Prometheus + OTel + Jaeger |
| Только `X-Request-Id` в логах без distributed tracing | Нет timeline spans и messaging- hops в одной картинке |
| Только метрики Task2 без трейсов | Видим *что* плохо с очередью, не *какой* `order_id` на каком hop |

### Последствия

**Станет лучше**

| Что | Как проявляется |
| --- | --- |
| Time-to-locate | От алерта Task2 → Jaeger по `order_id` → виновный span |
| Общий язык с логами (Task4) | Один `trace_id` в span и в structured log |
| Качество async-пайплайна | Broken traces (publish без consume) видны как сигнал, не только depth |

**Станет хуже / дороже (принимаем)**

| Что | Цена |
| --- | --- |
| Нагрузка на бэкенд | SDK + экспорт OTLP в каждом API / consumer |
| DevOps | Collector, Jaeger, sampling + **retention 7–14 дней**, доступ UI |
| Дисциплина атрибутов | Без запрета PII трейсы становятся утечкой |

### Недостатки, ограничения, риски

| Риск | Митигация |
| --- | --- |
| «Дыры» в следе без AMQP propagation | W3C + `order_id` в headers на publish/consume CRM↔MES и calc; тест broken trace rate |
| Потеря `order_id` при async | Дубль: span attribute **и** AMQP header; не опираться только на baggage |
| Нагрузка SDK / шум spans | ~10% sampling + always-on critical; не инструментировать UI/DB internals |
| Рост диска Jaeger | Retention 7–14 дней; memory — только в демо 3.1 |
| Ложное спокойствие «трейс зелёный» / «SLA из spans» | P0 = DLQ / age calc (Task2); из трейсов в алерт — только spanmetrics latency/errors |
| Jaeger UI доступен извне | Нет public ingress; VPN/SSO; review сетевых политик |
| Outbox/DLQ ещё внедряются (Task1 P0) | Атрибуты и spans закладываем сразу; до появления — хотя бы HTTP + текущий Rabbit path |

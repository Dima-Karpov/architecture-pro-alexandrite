### Функциональные требования

Нужны общие логи по пути заказа. Бизнес-логику Shop / CRM / MES не меняем.

Метрики уже в [Task2](../Task2/Выбор%20и%20настройка%20мониторинга%20в%20системе.md), трейсы — в [Task3](../Task3/Архитектурное%20решение%20по%20трейсингу.md). Логи отвечают на простой вопрос: **что случилось с этим заказом** (`order_id`).

| **№** | **Кто** | **Сценарий** | **Что пишем в лог** |
| :---: | :--- | :--- | :--- |
| UC1 | Клиент, Shop API | Заказ с сайта | Создали заказ, сменили статус, ошибка записи (без файла 3D) |
| UC3 | Партнёр, MES API, RabbitMQ, CRM API | Заказ через API | Приняли → отправили в очередь → CRM забрал; отказ / DLQ |
| UC4 | MES API, очередь расчёта | Расчёт цены | Поставили в очередь, начали, закончили, статус PRICE_CALCULATED |
| UC6 | CRM ↔ RabbitMQ ↔ MES | Смена статусов | Старый → новый статус + `order_id` + `trace_id` |

### Нефункциональные требования

| **№** | **Требование** |
| :---: | :--- |
| O2 | Логи структурированные (JSON). В каждой записи — `order_id` и `trace_id`. Без телефона, email, ФИО. |
| L1 | По номеру заказа в Kibana за минуты видно цепочку событий. |
| L2 | Стек: приложение → Filebeat → Logstash → Elasticsearch → Kibana. Есть ILM (срок жизни индексов). |
| L3 | Kibana только из VPN + SSO. Чувствительные поля режем в Logstash. |
| L4 | Свой индекс на сервис. Храним ~30 дней. |
| L5 | Очереди по-прежнему алертим из Prometheus ([Task2](../Task2/Выбор%20и%20настройка%20мониторинга%20в%20системе.md)). Из логов — только разбор и редкие аномалии. |

### Решение

#### 1. Откуда собираем логи (C4)

Это инициатива 4 из [Task1](../Task1/Планирование%20анализ%20идентификация%20проблем%20и%20поиск%20решений.md). На to-be уже есть ELK — здесь уточняем источники.

Схема (синим — что логируем и сам ELK):

- [`c4/01-logging.puml`](c4/01-logging.puml) · [`c4/01-logging.svg`](c4/01-logging.svg)

Общий контекст: [as-is](../Task1/c4/01-containers-as-is.puml) · [to-be](../Task1/c4/02-containers-to-be-6m.puml).

| Система | Берём в ELK? | Почему |
| --- | :---: | --- |
| CRM API, MES API | да, **сначала** | Партнёрский заказ, статусы, очередь, DLQ — главная боль |
| Shop API | да, **вторым** | Заказы с сайта; тот же `order_id` |
| События очереди | да, **из кода API** | Publish / consume пишем в приложении |
| API Gateway | потом | Access / 429 полезны, но статус заказа не объясняют |
| UI (Shop / CRM / MES) | нет | Шум браузера; кейс про сервер |
| PostgreSQL, S3 «изнутри» | нет | Достаточно ERROR в API |
| Prometheus, Jaeger | нет как источник INFO | Другие столпы; в лог кладём только `trace_id` для связи |

#### 2. Какие логи пишем

Формат — **JSON**, одна строка = одно событие.

Общие поля: `ts`, `level`, `service`, `event`, `order_id`, `customer_id` (внутренний id, не ФИО), `status_from` / `status_to`, `trace_id`, `msg`.

##### 2.1. Уровень INFO (обязательный список)

| Событие | Где | Что ещё в полях | Зачем |
| --- | --- | --- | --- |
| `order.created` | Shop / MES (partner) | `source=ui` или `partner` | Заказ появился |
| `order.status_changed` | Shop / CRM / MES | `status_from`, `status_to` | Как в задании: время + id покупателя + номер заказа + статус |
| `order.accepted_partner` | MES | `partner_id` | Партнёрский вход |
| `messaging.published` | CRM / MES | имя очереди | Ушло в Rabbit |
| `messaging.consumed` | CRM / MES | имя очереди | Дошло до consumer |
| `calc.enqueued` / `started` / `finished` | MES | `duration_ms` на finish | Путь до расчёта цены |
| `outbox.relayed` | CRM / MES | — | Из БД реально ушло в очередь |
| `dlq.parked` | CRM / MES | `reason` (код, без всего тела сообщения) | Битое сообщение |

Пример смены статуса:

```json
{
  "ts": "2026-11-23T15:04:05Z",
  "level": "INFO",
  "service": "crm-api",
  "event": "order.status_changed",
  "order_id": "ord_9f3a",
  "customer_id": "cust_12ab",
  "status_from": "NEW",
  "status_to": "PRICE_CALCULATED",
  "trace_id": "4bf92f…",
  "msg": "order status changed"
}
```

##### 2.2. Другие уровни

| Уровень | Когда включаем | На проде |
| --- | --- | --- |
| **ERROR** | Сломалось: 5xx, упал consume, ушло в DLQ | всегда |
| **WARN** | Повтор, 429, circuit open | всегда |
| **INFO** | Штатные события из таблицы выше | всегда |
| **DEBUG** | Детали для отладки (SQL, headers) | нет по умолчанию |
| **TRACE** | Очень подробный шум | только локально |
| **FATAL** | Сервис не стартует | редко + алерт |

В лог **нельзя** класть: файл 3D, полный payload Rabbit, токены, пароли, email, телефон, адрес.

#### 3. Мотивация

Сейчас проблему рассказывает клиент или партнёр. Разработчики долго собирают картину по трём серверам.

- **Метрики** (Task2): «что-то плохо» (очередь выросла, много 5xx).
- **Трейсы** (Task3): «на каком шаге застряло».
- **Логи** (это задание): «что именно произошло с заказом №…».

| Сейчас | После |
| --- | --- |
| Письмо «заказ не получили» → grep по EC2 | В Kibana ищем `order_id` |
| Support часами ждёт логи от DevOps | Сам смотрит timeline событий |
| Непонятно, менялся ли статус | Есть история `order.status_changed` |

**На что влияет внедрение** (3–5 метрик):

1. Время поиска причины по жалобе — падает (минуты вместо часов).
2. Доля тикетов Support без эскалации на backend — растёт.
3. Время починки после алерта — короче (ERROR + тот же `trace_id` в Jaeger).
4. Партнёрский churn из‑за «потеряли заказ» — снижается (часто находим раньше).
5. Запросы «скиньте логи с серверов» к DevOps — реже.

##### 3.1. Что делаем сначала (логи + трейсинг)

Всё сразу команда не успеет. Порядок как в Task1: сначала деньги и заказы.

| Очередь | Системы | Почему |
| --- | --- | --- |
| **1** | MES API + CRM API + события очереди / DLQ / Outbox | «Заказ не получен», статусы, партнёры |
| **2** | Shop API | Заказы с сайта |
| **3** | API Gateway | Потом: access и rate limit |
| **не берём** | UI, внутренности БД/S3 | Не закрывают главную боль |

Логи и трейсы на шаге 1 ставим **вместе** на CRM/MES — один `trace_id` и в span, и в JSON.

#### 4. Предлагаемое решение

Берём **ELK**, как в курсе и на to-be Task1.

| Часть | Что ставим | Зачем |
| --- | --- | --- |
| В приложении | JSON-логи (Logback / Serilog) | Искать по полям, не читать прозу |
| Сбор | **Filebeat** на EC2 | Забирает файлы/stdout |
| Обработка | **Logstash** | Парсит, добавляет `env`, вырезает PII |
| Хранение и UI | **Elasticsearch + Kibana** | Поиск по `order_id` / `trace_id` |
| Связка | те же id, что в Task3 | Алерт → Jaeger → Kibana без второго номера |
| Индексы | `logs-shop-api-*`, `logs-crm-api-*`, `logs-mes-api-*` | Проще хранить и чистить по сервису |

Схема: [`c4/01-logging`](c4/01-logging.puml).

Один простой пайплайн. Без ML и без второго набора алертов на очереди.

#### 5. Безопасность

| Тема | Как |
| --- | --- |
| Чувствительные данные | Не пишем: ФИО, телефон, email, адрес, карты, токены, пароли, 3D, полное тело сообщения |
| Что можно | Внутренние id: `order_id`, `customer_id`, `partner_id` |
| Защита на входе в ES | Logstash маскирует/дропает опасные поля |
| Кто смотрит | VPN + SSO. Support — чтение. DevOps — индексы и алерты |
| Из интернета | ES и Kibana наружу не открываем |
| DEBUG на проде | Выключен. Временно — только с тикетом и сроком |

#### 6. Хранение

| Параметр | Решение |
| --- | --- |
| Индекс | Отдельный на сервис (`logs-crm-api-*` и т.д.) |
| Поля для поиска | `order_id`, `customer_id`, `trace_id`, `event`, `service`, `level` — keyword; `ts` — date |
| Срок | **~30 дней**: 7 дней «горячие», дальше warm, потом удаление |
| Ролловер | По размеру шарда (~20–40 ГБ) или раз в день — что раньше |
| Объём (оценка) | ~**0,5–1 ГБ/сервис/сутки** на INFO critical path (3 API ≈ **1,5–3 ГБ/сутки**) → на 30 дней **~50–90 ГБ** (+ replica). Уточним по baseline на staging; квота диска ES и владелец индексов — DevOps |
| Удаление | ILM удаляет **индексы целиком**, не по одной записи |

#### 7. От сбора к анализу

Собрать логи мало — ими надо пользоваться.

| Нужно? | Что делаем |
| --- | --- |
| Алертинг | Да, узко. Канал: Kibana Alerting → чат команды / тикет (тот же контур, что Alertmanager в Task2). Владелец правил — DevOps |
| Аномалии | Да. Старт: `order.created` rate за **1 мин > 10× median** за час **или** абсолютный всплеск уровня примера курса (~4 → **10 000/с**) → тикет (flood / DDoS / баг клиента). Параллельно смотрим 429 на Gateway (Task2) |
| Пороги (старт) | ERROR: **> 1%** логов сервиса за 5 мин **или** ≥ **20** ERROR/мин; `dlq.parked`: **> 0** за 5 мин. Калибруем после baseline |
| Алерты очередей из ES | Нет. Depth / age / DLQ уже в Prometheus |
| ML в Elastic | Нет сейчас — хватает простых правил |
| Дашборды | Saved search по `order_id`; график по `event` / `level` |
| Связка с трейсом | В инциденте один `trace_id` → Jaeger и Kibana |

#### 8. Сравнение технологий (≥ 5 критериев)

Выбор: **ELK**. OpenSearch — запасной, если упрёмся в лицензию. Splunk — дорого. Loki — дешевле рядом с Grafana, но не то, что в курсе и на схеме Task1.

| Критерий | ELK (берём) | OpenSearch | Splunk | Grafana Loki |
| --- | --- | --- | --- | --- |
| Лицензия | Elastic License | Apache 2.0 | Проприетарная | AGPL |
| Курс / to-be Task1 | Совпадает | Похож | Нет в спринте | Не ELK |
| Поиск по `order_id` | Хороший | Хороший | Хороший | Слабее full-text |
| Цена для нас на EC2 | Средняя | Средняя | Высокая | Ниже, если уже Grafana |
| Кто умеет крутить | Много гайдов | Как ES | Нужен опыт Splunk | Проще при стеке Grafana |
| Алерты / аномалии | Kibana Alerting | Есть | Сильные | Grafana Alerting |
| Vendor lock | Средний | Ниже | Высокий | Средний |

Пересмотр: license → OpenSearch; диск/CPU ELK не тянем → Loki.

### Альтернативы

| Вариант | Почему нет |
| --- | --- |
| Логи только на диске EC2 + SSH | Долго искать; Support без доступа |
| Сразу Loki вместо ELK | Удобно с Grafana, но ломает сдачу и to-be |
| Splunk | Дорого для нашего масштаба |
| Логи без `order_id` / `trace_id` | Не склеить с метриками и трейсами |
| DEBUG на весь прод | Дорого и опасно по данным |
| Все алерты только из логов | Хуже, чем метрики для очередей |

### Последствия

**Лучше:** быстрее разбор по `order_id`; меньше нагрузки на Support; одна цепочка Alert → Trace → Log.

**Дороже:** крутить ES/Logstash/Filebeat; следить за полями (иначе утечка); без ILM диск забьётся.

### Недостатки, ограничения, риски

| Риск | Что делаем |
| --- | --- |
| В лог попадут телефон / email | Список запрещённых полей + redact в Logstash + code review |
| Индексы раздуются | Только INFO из списка; ILM 30 дней |
| Logstash отстанет | Смотрим lag; алерт на drop |
| `trace_id` в логах и в Jaeger разные | Один общий способ прокидывать id (как в Task3) |
| Много ложных алертов из Kibana | Только ERROR, аномалия create, dlq; очереди — в Prometheus |
| Shop во второй очереди | Партнёрский путь важнее; сайт подключаем следом |

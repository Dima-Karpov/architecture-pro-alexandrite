### Решение

#### 1. Краткий анализ C4

Новых контейнеров в Task2 не добавляем: Prometheus / Grafana / Alertmanager уже на to-be в Task1. Зелёный алертинг (правила в проде) — контур Task3 по курсу не требуется здесь; алерты на P0-сигналы планируем в этом ADR как часть мониторинга.

- To-be (6 мес): [`Task1/c4/02-containers-to-be-6m.puml`](../Task1/c4/02-containers-to-be-6m.puml) · [`Task1/c4/02-containers-to-be-6m.svg`](../Task1/c4/02-containers-to-be-6m.svg)

Контур наблюдения:

| Слой C4 | Что закрываем метриками |
| --- | --- |
| Shop / CRM / MES API (+ partner через Gateway) | RED: RPS, ошибки, latency |
| EC2 API, PostgreSQL, RabbitMQ | USE: utilization, saturation, errors |
| Очереди CRM↔MES и расчёта цены | Depth / age / in-flight / DLQ — «заказ в пути» |
| Internet Shop UI | Яндекс Метрика (как сейчас); не заменяет API/MES |

#### 2. Мотивация

У «Александрита» три боли кейса. Метрики нужны чтобы **раньше клиента** увидеть каждую:

| Боль | Без метрик | С метриками |
| --- | --- | --- |
| Партнёр: заказ не получен | Узнаём от менеджера партнёра → churn | DLQ / depth / age / in-flight → triage / replay до жалобы |
| Заказ завис до PRICE_CALCULATED | «Где заказ?» по почте через часы | Age очереди расчёта > порога → алерт |
| Дашборд MES тормозит / API тупит | Операторы и партнёры уже страдают | Latency MES + DB connections + RED API |

Яндекс Метрика считает клики на сайте. Partner API, CRM consumer и RabbitMQ она не видит. **Мотивация:** без наших метрик о потерянном заказе узнаём от менеджера партнёра — уже после churn.

#### 3. Выбор подхода к мониторингу

Не витрина всех трёх «везде»: один главный язык на слой.

| Часть системы | Подход | Почему |
| --- | --- | --- |
| Shop / CRM / MES API (+ partner через Gateway) | **RED** | HTTP-сервисы; request path смотрят Rate / Errors / Duration |
| EC2 API, PostgreSQL, RabbitMQ | **USE** | Ресурсы и брокер: Utilization + Saturation + Errors |
| Сквозное «здоровье заказа» | **Четыре золотых сигнала** как рамка алертов | Трафик + ошибки + задержка + **насыщенность очереди** бьют в «заказ не дошёл» / залипание PRICE_CALCULATED |
#### 4. Метрики

Выбор из списка курса (п. 1–40) + немного extras. Номер — позиция в списке задания. Ярлыки — только низкая кардинальность: `service`, `route` / `queue`, `status`, `env`, `instance` (и `db` / `resource` где нужно). Без `user_id`.

Очереди в Rabbit смотрим **две**: CRM↔MES (статусы) и **очередь расчёта цены** (до PRICE_CALCULATED; до ~30 мин — норма, дольше — проблема).

##### 4.0. Словарь ярлыков

Ярлык (label) — это **измерение (срез)** одной метрики, а не отдельная метрика: одна серия, разные значения ярлыков. Пример: `http_requests_total{service="shop-api",route="partner",status="500",env="prod"} 12`.

| Ярлык      | Значение                       | Примеры значений                            |
| ---------- | ------------------------------ | ------------------------------------------- |
| `env`      | окружение                      | `prod`, `release`, `dev`                    |
| `service`  | какой API / компонент          | `shop-api`, `crm-api`, `mes-api`, `gateway`, `calc-worker` (после изоляции calc, Task1 P2) |
| `instance` | конкретный EC2 / инстанс       | hostname / instance id                      |
| `queue`    | имя очереди RabbitMQ           | `crm-mes`, `calc-price`, `dlq`              |
| `route`    | HTTP-маршрут или зона API      | `/orders`, `partner`, `mes-dashboard`       |
| `status`   | HTTP status (или класс)        | `200`, `429`, `500`                         |
| `db`       | какая БД                       | `shop-db`, `mes-db`                         |
| `resource` | тип ёмкости (диск / хранилище) | `s3`, `shop-db-disk`, `mes-db-disk`         |

##### 4.1. «Заказ не дошёл» / битое сообщение (P0)

| Проблема                      | Метрика                                            |     №      | Зачем                                                                              | Ярлыки         |
| ----------------------------- | -------------------------------------------------- | :--------: | ---------------------------------------------------------------------------------- | -------------- |
| Заказ сломан / не обработан   | Number of dead-letter-exchange letters in RabbitMQ |     1      | Consumer N раз упал → сообщение в «парковку»; алерт сразу, не ждём письмо партнёра | `queue`, `env` |
| Consumer завис / умер         | Number of message in flight in RabbitMQ            |     2      | Рост без прогресса = завис; 0 при растущей очереди = consumer умер                 | `queue`, `env` |
| Backlog «заказ в пути»        | Queue depth (сообщения в ожидании)                 | вне списка | Очередь растёт → заказы ещё не в CRM / не досчитаны                                | `queue`, `env` |
| Залипание до PRICE_CALCULATED | Age самого старого сообщения                       | вне списка | Даже при малой depth одно сообщение может висеть часами                            | `queue`, `env` |

##### 4.2. «API / сайт отдают ошибку или тормозят» (RED)

| Проблема | Метрика | № | Зачем | Ярлыки |
| --- | --- | :---: | --- | --- |
| Непонятен фон нагрузки | Number of requests (RPS) for internet shop API | 3 | Без RPS 10 ошибок — шум или катастрофа; всплеск partner виден на `route` | `service`, `route`, `env`, `instance` |
| То же для CRM | Number of requests (RPS) for CRM API | 4 | Фон consumer/API CRM vs инцидент | `service`, `route`, `env`, `instance` |
| То же для MES / partner | Number of requests (RPS) for MES API | 5 | Partner path и дашборд — разные `route` | `service`, `route`, `env`, `instance` |
| Клиент / партнёр долго ждёт | Response time (latency) for shop API | 19 | Duration в RED; **Histogram**, алерт/дашборд по **p95**, не по avg | `service`, `route`, `env` |
| CRM тормозит | Response time (latency) for CRM API | 20 | То же: Histogram → p95 | `service`, `route`, `env` |
| MES / дашборд тормозит | Response time (latency) for MES API | 21 | Histogram → p95; отдельный `route` списка заказов — боль операторов | `service`, `route`, `env` |
| Shop API отказывает | Number of HTTP 500 for shop API | 28 | Явный отказ; скачок 5xx = инцидент на API | `service`, `route`, `status`, `env` |
| CRM API отказывает | Number of HTTP 500 for CRM API | 29 | Отказ CRM на critical path заказа | `service`, `route`, `status`, `env` |
| MES API отказывает | Number of HTTP 500 for MES API | 30 | Отказ MES / partner / дашборда | `service`, `route`, `status`, `env` |

HTTP 200 (п. 25–27) **отдельно не заводим**: один counter с ярлыком `status` → успех и 4xx/5xx из одной серии. Иначе три дубля.

##### 4.3. «Почему тормозит / упрёмся в железо» (USE)

RED говорит *что плохо пользователю*. CPU / mem / DB — *хватит ли машины*.

| Проблема | Метрика | № | Зачем | Ярлыки |
| --- | --- | :---: | --- | --- |
| API упёрся в CPU | CPU % for shop API | 9 | Высокий CPU + растущая latency → 2-й инстанс / оптимизация, не «магия очереди» | `service`, `instance`, `env` |
| | CPU % for CRM API | 10 | То же для CRM | `service`, `instance`, `env` |
| | CPU % for MES API | 11 | Пока calc в MES API — `service=mes-api` + `queue`/`route=calc-price`; после изоляции worker’а (Task1 P2) — отдельный `service=calc-worker`, иначе слепота | `service`, `instance`, `env` |
| Утечки / OOM | Memory Utilisation for shop API | 12 | OOM → рестарты → потеря inflight / обрывы | `service`, `instance`, `env` |
| | Memory Utilisation for CRM API | 13 | То же для CRM | `service`, `instance`, `env` |
| | Memory Utilisation for MES API | 14 | То же для MES; calc — как у CPU №11 (`mes-api` сейчас → `calc-worker` позже) | `service`, `instance`, `env` |
| БД под давлением | Memory Utilisation for shop db instance | 15 | Shared Shop DB: на ней сидят и Shop API, и CRM API — метрика покрывает оба | `db=shop-db`, `instance`, `env` |
| | Memory Utilisation for MES db instance | 16 | Дашборд / список заказов бьёт MES DB | `db=mes-db`, `instance`, `env` |
| Пул кончился | Number of connections for shop db instance | 17 | CRM → та же Shop DB: №17 покрывает и CRM; 5xx «из ниоткуда», пока CPU ещё жив | `db=shop-db`, `instance`, `env` |
| | Number of connections for MES db instance | 18 | Частая причина «MES лежит» для операторов | `db=mes-db`, `instance`, `env` |
| Диск кончится (не P0 сегодня) | Size of S3 storage | 22 | Warning на горизонт недель, не инцидент «сейчас» | `resource`, `env` |
| | Size of shop db instance | 23 | То же для Shop DB | `resource`, `env` |
| | Size of MES db instance | 24 | То же для MES DB | `resource`, `env` |

##### 4.4. Добавки сверх списка (из Task1)

| Проблема | Метрика | Зачем | Ярлыки |
| --- | --- | --- | --- |
| «В CRM есть, в MES нет» | Outbox lag (неотправленные строки) | БД обновили, в Rabbit ещё не ушло | `service`, `env` |
| Лавина на consumer’ах | Gateway 429 на partner | Ловим перегруз / backpressure до завала очереди | `route=partner`, `env` |
| Дашборд MES тормозит | Latency списка заказов MES | Боль операторов; база для оценки кеша (Task5) | `service=mes`, `route=orders_list`, `env` |

##### 4.5. Сознательно не берём

| Не берём | № | Почему бесполезно *для наших болей* |
| --- | :---: | --- |
| Number of requests (RPS) per user for internet shop / CRM / MES API | 6–8 | Тысячи рядов в Prometheus; для потери заказов не нужно. Нагрузку partner — по `route=partner` |
| Number of HTTP 200 for shop / CRM / MES API | 25–27 | Дубль: успех читаем из того же counter с `status` (см. §4.2) |
| Number of HTTP 500 for shop API *(повтор)* | 31 | Мусор списка курса |
| Number of simultanious sessions for shop / CRM / MES API | 32–34 | Почти то же, что RPS + CPU |
| Kb tranferred (received) / Kb provided (sent) for shop / CRM / MES API | 35–40 | Трафик сети ≠ «заказ дошёл» |

#### 5. План действий

Высокоуровневое ТЗ на внедрение (не docker-compose в репо). Стек как на to-be Task1: **Prometheus (pull) + Grafana + Alertmanager**.

| Шаг | Что сделать | Детали |
| :---: | --- | --- |
| 1 | Инстансы стека | Prometheus + Grafana + Alertmanager на managed/VM; scrape **prod** и **staging**; Alertmanager → тикет / чат команды (без «звонилки» на warning). |
| 2 | Exporters | **node_exporter** на EC2 API (в т.ч. будущий `calc-worker`); **postgres_exporter** на **Shop DB** (shared Shop+CRM) и MES DB; **rabbitmq_exporter** на брокер (queues CRM↔MES, calc, DLQ). |
| 3 | App `/metrics` | Shop / CRM — Micrometer (Spring); MES — prometheus-net или OTel metrics → scrape Prometheus. Ярлыки §4. Latency: **Histogram** (`http_request_duration_seconds` или аналог); дашборд и алерты по **p95**, не по avg. Пока calc в процессе MES — метки на `mes-api` + `queue`/`route=calc-price`; после выноса — scrape `service=calc-worker`. |
| 4 | Дашборды Grafana | **Order path** — RED + DLQ / depth / age / in-flight / outbox; **Saturation** — USE CPU/mem/DB connections; **MES ops** — latency `route=orders_list`. |
| 5 | Алерты P0 | Правила в Alertmanager на сигналы §6 (DLQ, age calc, 5xx, connections). Warning на size DB/S3 — не P0. |
| 6 | Runbook | У каждого P0-алерта ссылка на действие из §6 (тикет / scale / разбор DLQ / replay). Без runbook алерт не включаем. |

**Rollout (один DevOps):**

1. Стек + rabbitmq_exporter + алерты DLQ / age calc / 5xx.
2. `/metrics` в приложениях + дашборд Order path.
3. postgres/node exporters + дашборд Saturation + алерты connections/CPU/mem.
4. Outbox lag + Gateway 429 + MES ops dashboard — после появления метрик в коде (Task1 P0).

#### 6. Насыщенность — пороги и действия

Стартовые пороги; калибруем по baseline staging/prod. Норма кейса: расчёт цены до **~30 мин**.

| Сигнал                    | Порог                                                       | Severity | Действие                                                                      |
| ------------------------- | ----------------------------------------------------------- | :------: | ----------------------------------------------------------------------------- |
| DLQ letters               | > 0 sustained **5 мин** **или** рост ≥ **5**/час            |    P0    | Разбор payload/`order_id` → replay / fix / drop с аудитом                     |
| Age очереди расчёта       | > **45 мин**                                                |    P0    | Тикет на calc worker; CPU/mem MES; эскалация, если age растёт                 |
| Depth CRM↔MES             | Рост ≥ **50** сообщ. за **15 мин** **и** in-flight ≈ 0      |    P0    | Consumer down → рестарт / scale; проверить CRM API                            |
| In-flight                 | > **2×** обычного baseline **10+ мин** при стабильной depth |    P1    | Зависший consumer → рестарт; снизить prefetch                                 |
| HTTP 5xx (shop/CRM/MES)   | > **1%** запросов **5 мин** **или** ≥ **20** 5xx/мин        |    P0    | Инцидент API; RED + CPU/mem; rollback / hotfix                                |
| Latency MES `orders_list` | p95 > **2 с** sustained **10 мин**                          |    P1    | Тикет на MES/DB; кандидаты — connections, потом кеш (Task5)                   |
| DB connections            | > **80%** max pool sustained **5 мин**                      |    P0    | Искать leak; осторожно поднять pool; read-replica — по факту (P2 Task1)       |
| CPU API                   | > **85%** **10+ мин** + растущая latency                    |    P1    | Scale-out 2-й инстанс за Gateway **или** оптимизация hot path                 |
| Memory API                | > **90%** **или** OOM restart                               |    P0    | Heap dump / фикс утечки; не маскировать бесконечным scale                     |
| Outbox lag                | Рост ≥ **20** строк за **10 мин** **или** lag > **5 мин**   |    P0    | Relay down / Rabbit недоступен → починить publish path                        |
| Gateway 429 partner       | Spike ≥ **10**/мин sustained **5 мин**                      |    P1    | Ожидаемый backpressure; валидный клиент — пересмотреть лимит; иначе защита ок |
| Size DB / S3              | Тренд к лимиту за **2–4 недели**                            | Warning  | Тикет на диск / lifecycle S3; не пейджер                                      |

### Альтернативы

| Вариант                            | Почему не берём                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------ |
| Только Яндекс Метрика              | Не видит Partner API, CRM consumer, RabbitMQ; time-to-detect = жалоба партнёра |
| Datadog / YC Monitoring all-in-one | Дороже / vendor lock; курс и to-be Task1 уже на Prometheus + Grafana;          |
| Только CPU/mem без RED и очередей  | «Машина жива», а заказы в DLQ / age calc растёт — слепые к P0 кейса            |
| Все 40 метрик курса + per-user RPS | Шум, кардинальность, алерт-флуд; не приближает к «заказ дошёл»                 |

### Последствия

Что **станет иначе** после принятия решения (не «если повезёт / не повезёт» — это риски ниже).

**Станет лучше**

| Что | Как проявляется |
| --- | --- |
| Time-to-detect по заказам | DLQ / age calc / 5xx partner будят команду до письма партнёра |
| Общий язык инцидентов | RED на API + USE на железо/очередь — меньше споров «это сеть или CRM» |
| Решения о масштабе | Scale-out / replica — по saturation, а не по ощущениям |
| База для Task3–5 | Метрики заказанного пути есть до трейсов, логов и кеша |

**Станет хуже / дороже (принимаем)**

| Что | Цена |
| --- | --- |
| Нагрузка на DevOps | Ещё один стек: Prometheus, Grafana, Alertmanager, exporters, scrape-конфиг |
| Время бэкенда | `/metrics` в Shop/CRM/MES, ярлыки, сопровождение при смене API |
| Шум на старте | Пороги §6 первые недели будут «плавать» → ложные алерты, пока нет baseline |
| Операционная зависимость | Упал Prometheus / забыли scrape — снова слепые; нужен хотя бы алерт `up==0` |
| Внимание команды | Часть спринта уходит на дашборды и runbook вместо фич |
| Дисциплина алертов | Без владельца и runbook (§6) мониторинг превращается в «картинки», которые никто не смотрит |

### Недостатки, ограничения, риски

Риски — то, что **может пойти не так**; митигация обязательна. Отдельно от принятых последствий выше.

| Риск | Митигация |
| --- | --- |
| Высокая кардинальность labels (`user_id`, per-route без лимита) | Только `service` / `route` / `queue` / `status` / `env` / `instance`; без per-user |
| Алерт-шум → игнор P0 | Мало алертов на critical path; пороги калибруем; runbook обязателен |
| Один DevOps на весь стек | Rollout: queues+5xx → USE DB → остальное; не всё в один день |
| Метрики без владельца runbook | К каждому P0-алерту — действие в §6 |
| Ложное спокойствие «графики зелёные» | SLI на заказной путь (DLQ, age calc, 5xx partner), не на красоту дашборда |
| Outbox/DLQ ещё не в коде (Task1 P0) | Метрики и алерты закладываем сразу; до внедрения — хотя бы depth/age/in-flight брокера |

### Название задачи:

ALX-ADR-1. Планирование целевой архитектуры «Александрит» на 6 месяцев: проблемы, инициативы, приоритеты

### Функциональные требования

Контур заказа ювелирных изделий на заказ. Горизонт — шесть месяцев. Бизнес-логику Shop / CRM / MES в этом ADR не меняем: фиксируем as-is потоки и требования к надёжности и наблюдаемости вокруг них.

| **№** | **Действующие лица или системы** | **Use Case** | **Описание** |
| :---: | :--- | :--- | :--- |
| UC1 | Customer, Internet Shop UI, Shop API, Shop DB, S3 | Заказ из витрины | Клиент оформляет заказ, загружает / редактирует 3D-модель. Shop API пишет заказ в Shop DB, модель — в S3. |
| UC2 | Seller, CRM UI, CRM API, Shop DB | Ведение заказа в CRM | Продавец ведёт заказ клиента. CRM API читает/пишет ту же Shop DB. |
| UC3 | API user, MES API, RabbitMQ, CRM API | Партнёрский заказ через API | Партнёр создаёт заказ через MES API. Сообщение уходит в RabbitMQ; CRM consumer создаёт заказ в CRM/Shop DB. |
| UC4 | MES API, S3, очередь расчёта | Расчёт цены | MES считает цену по 3D-модели (2–30 мин), статус доходит до PRICE_CALCULATED. Производство не bottleneck. |
| UC5 | Operator, MES UI, MES API, MES DB | Дашборд и взятие в работу | Оператор видит список заказов и берёт заказ в работу. |
| UC6 | CRM API ↔ RabbitMQ ↔ MES API | Смена статусов | Статусы заказа синхронизируются между CRM и MES через очередь. |

### Нефункциональные требования

| **№** | **Требование** |
| :---: | :--- |
| R1 | Партнёрский заказ (UC3) не теряется: доставка в CRM либо успешна, либо видна в DLQ с возможностью replay / triage. |
| R3 | Публикация в Rabbit после смены статуса в БД атомарна относительно outbox (нет «в БД есть, в очередь не ушло»). |
| R2 | Инцидент «заказ не дошёл / завис» обнаруживается системой раньше жалобы клиента (метрики очереди, алерты, корреляция по `order_id`). |
| P1 | Дашборд MES (UC5) остаётся пригодным для операторов при росте объёма (+100 заказов/мес и внешний API). |
| P2 | Публичный partner API выдерживает всплески без лавины на consumer’ах (rate limit на API Gateway / backpressure / ограниченный prefetch). |
| O1 | RED/ошибки API, глубина/age очередей (в т.ч. расчёта цены), DLQ, latency дашборда, насыщение CPU/mem/DB — в мониторинге с алертами. |
| O2 | Сквозной след Shop→CRM→MES→очередь: `trace_id` + `order_id`; структурированные логи смены статуса без PII в cleartext. |
| S1 | Три приложения уже разделены; за 6 месяцев не уходим в microservices cutover и не делаем K8s production cutover (spike 3.1 — отдельно). |
| +R1 | Стек as-is: Shop/CRM — Vue + Spring Boot; MES — React + C#; PostgreSQL; RabbitMQ; S3; EC2 / Managed DB. |

### Решение

#### Проблемы (существующие и потенциальные)

Симптомы кейса: просрочки относительно обещания «3 недели», «заказы не дошли» у API-партнёров, медленный дашборд MES, потеря контрактов, рост нагрузки.

| Группа | Контейнеры | Суть |
| --- | --- | --- |
| Надёжность пайплайна | RabbitMQ, CRM API, MES API | Потеря/залипание сообщений (нет retry/идемпотентности) → «заказ не получен»; долгий PRICE_CALCULATED без контроля очереди расчёта |
| Битые / необработанные сообщения | RabbitMQ, CRM/MES consumer’ы | Publisher отправил, consumer упал/отклонил — сообщение исчезает или крутится вечно; нет parking-lot для разбора и решения |
| Надёжность публикации | CRM API, MES API | БД обновили, а в Rabbit не ушло (или наоборот) — нет Transactional Outbox |
| Coupling / SPOF данных | Shop DB | Одна shared Shop DB на Shop API и CRM API: сильный coupling, общая точка отказа и конкуренция за R/W при росте нагрузки |
| Производительность MES | MES UI, MES API, MES DB | Дашборд тормозит при росте объёма; пагинация не спасла → чтение «горячих» заказов бьёт MES DB |
| Ёмкость / SPOF | Shop/CRM/MES API, Shop DB, MES DB | Один инстанс на сервис и одна БД R/W; линейный рост + внешний API |
| Observability | все API, RabbitMQ | Нет метрик/трейсов/корр. логов по `order_id` → узнаём от клиентов; Яндекс Метрика не покрывает API/MES |
| Процессы | релизный контур | Ручной E2E + блок релизов → долгий time-to-fix при инцидентах |
| Защита от перегруза | partner API, consumer’ы | Нет единой точки входа: rate limit / backpressure / circuit breaker размазаны или отсутствуют |

#### Инициативы

1. **Мониторинг + алерты** (Prometheus/Grafana): RED/ошибки API, глубина/age очередей (CRM↔MES **и очередь расчёта цены**), DLQ, latency MES dashboard, насыщение CPU/mem/DB. Алерт на depth/age calc-очереди — ловить «залипание» до PRICE_CALCULATED раньше жалобы клиента. → **Task2**
2. **Надёжность RabbitMQ (транспорт)**: retry+TTL, publisher confirms, идемпотентные consumer’ы CRM/MES, разумный prefetch. Сквозная база для Task3/4.
3. **Трейсинг** (OpenTelemetry → Jaeger): correlation / `trace_id` + `order_id` по Shop→CRM→MES→очередь. → **Task3**
4. **Централизованные логи** (ELK): структурированные INFO по смене статуса; без PII в cleartext; ILM. → **Task4**
5. **Кеш дашборда MES** (список заказов по статусам для операторов). → **Task5**  
   Выбор из вариантов курса:
   - **Где:** **серверное** (MES API ↔ Redis), не клиентское HTTP-кеширование в браузере оператора — у нескольких операторов должен быть общий согласованный снимок; браузерный кеш у каждого свой и плохо инвалидируется при «взяли заказ».
   - **Паттерн чтения:** **Cache-Aside** (при промахе MES API читает БД/replica и кладёт в Redis). Не Read-Through / Refresh-Ahead — меньше магии у кеш-слоя, приложение само контролирует ключ и свежесть; Refresh-Ahead гоняет фоновый прогрев списка, который часто меняется при гонке операторов.
   - **Паттерн записи:** **не Write-Through / Write-Behind** на список — смена статуса пишется в MES DB как сейчас; кеш списка не обязан быть write-path. После записи — инвалидация.
   - **Инвалидация:** **комбинация** — короткий **TTL (временная)** + **по ключу / программная** при смене статуса (появился / взяли / сменили) → сброс ключа списка. Иначе операторы видят устаревшие заказы (оплата «кто взял первым»).  
   Компромисс: до TTL/инвалидации заказ может появиться в UI с задержкой в секунды — это осознанно, не «вечный» кеш.
6. **API Gateway + backpressure**: единая точка входа (Shop/CRM/MES/partner); **rate limit** и маршрутизация на Gateway; prefetch на consumer’ах. Отдельные CRM LB / MES LB не заводим — баланс инстансов делает Gateway.
7. **Изоляция расчёта цены**: отдельный worker-пул / очередь calc, таймауты, Circuit Breaker к тяжёлым моделям.
8. **Масштаб по необходимости**: 2-й инстанс CRM/MES API **за API Gateway**; read-replica MES DB для дашборда.
9. **Ускорение поставки**: авто-smoke E2E на critical path заказа; ускорить hotfix-релиз.
10. **Найм (пакет):**
    - **+1 frontend React** — обязательно: MES на React, в команде только «частично знает React» при 2× Vue; дашборд и UX списка заказов упираются во фронт MES.
    - **+1 backend** (Java или C#) под RabbitMQ/интеграции **или** усиление DevOps/SRE под observability — одно по факту P0; React не взаимозаменяем с ними.
11. **Битые сообщения + надёжная публикация** (отдельно от п.2):
    - **Consume:** после N неудач → **DLX → DLQ / parking-lot**. Фиксируем payload, `order_id`, причину, timestamp. Алерт на рост DLQ. Процесс: разбор → replay / правка данных / drop с аудитом.
    - **Publish:** **Transactional Outbox** — смена статуса/заказа и запись в outbox в одной транзакции БД; relay публикует в Rabbit с confirms и помечает outbox sent.

#### Приоритеты

Критерий: **сначала остановить потерю денег и заказов, потом ускорить операторов, потом масштаб «на вырост».**

| Приоритет | Инициативы | Зачем |
| --- | --- | --- |
| **P0 (сейчас)** | 1, 2, **11**, 6 | Видеть путь (в т.ч. depth/age **очереди расчёта**, не только DLQ); не терять на publish/consume; не заваливать API |
| **P1 (квартал)** | 3, 4, 5 | Найти где «завис» заказ; ускорить MES |
| **P2 (к полугоду)** | 7, 8, 9, 10 | Запас по ёмкости и скорости фиксов |

Почему не «сразу Kubernetes / микросервисы»: три приложения уже разделены; сначала observability + очередь + кеш на текущих EC2/Managed DB.

#### Целевая архитектура через 6 месяцев

Тот же контур C4 (Shop / CRM / MES, Shop DB + MES DB, S3, RabbitMQ), плюс **API Gateway**, observability, Redis, Outbox+DLQ; по потребности — 2-й инстанс CRM/MES API за Gateway и read-replica MES DB. K8s на целевую схему не выносим (spike Task 3.1, не cutover за полгода).

На диаграмме to-be:

- **API Gateway** (Edge): HTTPS-вход UI и partner; route `/shop|/crm|/mes|/partner`; rate limit partner; баланс на 2-й инстанс (вместо отдельных CRM/MES LB)
- Observability: Prometheus + Grafana; **OpenTelemetry Collector** (SDK в Shop/CRM/MES API → OTLP) → Jaeger; ELK (shipper из API)
- Redis перед чтением списка заказов MES
- Messaging: RabbitMQ + **DLQ/parking-lot**; у CRM/MES API — **Outbox (+ relay)**
- По потребности: 2-й инстанс CRM/MES API за Gateway, read-replica MES DB

#### Top-3 на полгода (если можно только три)

1. **Мониторинг + алерты на критический путь заказа и RabbitMQ** — без этого чиним вслепую; алерты на DLQ **и** на depth/age очереди расчёта ловят «не получили» / залипание PRICE_CALCULATED раньше жалобы.
2. **Надёжность асинхронного пайплайна** (п.2 + **п.11** + backpressure): Outbox на отправку, DLQ на битые после consume, retry/идемпотентность, rate limit — прямое лекарство от «заказ не получен».
3. **Кеширование / ускорение дашборда MES** — **серверный Cache-Aside** + короткий TTL и инвалидация по ключу при смене статуса (не клиентский HTTP-кеш, не Write-Through/Refresh-Ahead). Список читается быстрее; свежесть — секунды, не «навсегда».

Трейсинг и логи остаются в полном плане как P1; при жёстком лимите «только 3» уступают пунктам, которые сразу режут churn и простой.

### Альтернативы

| Вариант | Почему не берём сейчас |
| --- | --- |
| Сразу Kubernetes / microservices cutover | Yagni: контур уже из трёх приложений; без observability и надёжной очереди K8s не чинит потерю заказов. Spike 3.1 — отдельно. |
| Только Яндекс Метрика / APM без алертов на очередь | Не покрывает API/MES/RabbitMQ; узнаём о проблеме от партнёра. |
| Кеш без мониторинга и DLX | Ускорит UI, но не остановит потерю партнёрских заказов. |
| Полный набор паттернов (saga, CQRS, service mesh) | Раздувает витрину; KISS — Outbox + DLQ/parking-lot + идемпотентность + rate limit + cache-aside. |
| Только publisher confirms без Outbox | Не закрывает «commit в БД прошёл, publish упал» между транзакцией и брокером. |
| Только retry без DLQ | Ядовитые сообщения крутятся вечно и блокируют очередь; нет места для triage. |
| Найм только backend/DevOps без React | MES UI на React; без выделенного фронта дашборд и UX останутся узким местом. |

### Недостатки, ограничения, риски

| Риск | Митигация |
| --- | --- |
| Идемпотентность consumer’ов потребует доработки CRM/MES API | Заложить в P0 вместе с п.2/11; без неё retry размножит заказы |
| Outbox relay отстаёт / DLQ растёт без владельца | Алерты на lag outbox и размер DLQ; runbook: replay / fix / drop с аудитом |
| Redis stale на дашборде | Короткий TTL + инвалидация по смене статуса (Task5) |
| Read-replica / 2-й инстанс без метрик — преждевременный масштаб | Сначала O1/алерты (P0), масштаб — P2 по факту насыщения |

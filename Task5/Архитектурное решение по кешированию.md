### Функциональные требования

Кеш не меняет бизнес-логику Shop / CRM / MES. Цель — быстрее читать список заказов на дашборде MES (инициатива 5 / Top-3 из [Task1](../Task1/Планирование%20анализ%20идентификация%20проблем%20и%20поиск%20решений.md)).

| **№** | **Кто** | **Сценарий** | **Что делаем с кешем** |
| :---: | :--- | :--- | :--- |
| UC5 | Оператор, MES UI, MES API, MES DB | Дашборд: список заказов по статусу | Читаем из кеша; при промахе — из БД и кладём в кеш |
| UC5 / UC6 | Оператор / CRM↔MES | Смена статуса, «взять в работу» | Пишем в MES DB как сейчас; после записи сбрасываем ключи списков |

### Нефункциональные требования

| **№** | **Требование** |
| :---: | :--- |
| P1 | Дашборд MES остаётся быстрым при росте объёма (+100 заказов/мес и partner API). |
| C1 | Несколько операторов видят **один** согласованный снимок: нельзя, чтобы у A заказ уже «взят», а у B ещё «свободен» на минуты. |
| C2 | Допустима задержка появления заказа в списке **секунды**, не минуты. |
| C3 | Если Redis упал — MES API читает БД напрямую (хуже по скорости, но работает). |
| C4 | Стек to-be: Redis рядом с MES API (EC2 / Managed), как на схеме Task1. |

### Решение

#### 1. Что кешируем

| Кешируем | Не кешируем |
| --- | --- |
| **Список заказов** дашборда MES: ключ вида `mes:orders:{status}:{page}` (и при необходимости фильтр) | Карточку одного заказа при редком открытии — пока не нужно |
| Горячий read-path операторов (много одинаковых GET) | Расчёт цены, 3D в S3, partner create — там другая боль (очередь / надёжность) |
| | Shop / CRM витрину — в этом ADR не трогаем |

Почему именно список: в кейсе операторы жалуются на первую страницу MES; пагинация не помогла; от свежих заказов зависит вознаграждение. Это чистый **read-heavy** путь в MES DB.

Жалобы клиентов на **скорость заказа** (просрочки, «не получили») этим ADR **не лечим** — это очередь / надёжность / мониторинг из Task1–4. Здесь только скорость **дашборда MES** для операторов.

Контекст: [as-is](../Task1/c4/01-containers-as-is.puml) · [to-be](../Task1/c4/02-containers-to-be-6m.puml) (Redis уже на to-be).

#### 2. Мотивация

| Сейчас | Проблема | Зачем кеш |
| --- | --- | --- |
| Каждый refresh дашборда → тяжёлый SELECT в MES DB | Страница тормозит, операторы ждут | Ответ из Redis за миллисекунды |
| Несколько операторов смотрят одни и те же статусы | Одна и та же выборка бьёт БД много раз | Один общий снимок на всех |
| Устаревший список после «взяли заказ» | У B ещё виден «свободный» заказ | Быстрая **инвалидация** при смене статуса |

Кеш чинит **устаревший снимок списка** (C1), а не гонку claim: два оператора всё равно могут нажать «взять» почти одновременно — это решается в БД (`UPDATE … WHERE status=…` / optimistic lock), не Redis.

**Элементы в кеш:** готовый JSON (или компактный DTO) страницы списка — не сырые строки всех таблиц. Модель в кеше может отличаться от схемы БД (плюс Cache-Aside).

На что смотрим после внедрения (связь с [Task2](../Task2/Выбор%20и%20настройка%20мониторинга%20в%20системе.md)):

1. p95 latency `orders_list` — должна упасть.
2. Hit rate Redis по ключам `mes:orders:*`.
3. Нагрузка на MES DB (connections / CPU) на чтении списка — вниз.
4. Алерт: Redis недоступен / hit rate резко упал (иначе молча бьём БД).

#### 3. Предлагаемое решение

##### 3.1. Клиентский или серверный?

| | Клиентский (HTTP Cache-Control в браузере) | Серверный (Redis у MES API) |
| --- | --- | --- |
| Кто хранит | Каждый браузер оператора **свой** кеш | Один Redis на всех |
| Сброс после «взяли заказ» | С сервера чужой браузер не сбросить | `DEL` ключа — все сразу видят miss |
| Согласованность | Плохая при гонке операторов | Хорошая для общего дашборда |
| Доп. инфраструктура | Нет | Redis (уже в плане Task1) |

**Берём серверный.** Клиентский HTTP-кеш оставляем только для статики UI (js/css/картинки), не для `GET /orders`.

Почему так лучше в проде для MES: общий read-cache + явный invalidate на write — обычная схема для админских списков; браузерный `max-age` на API списка здесь вреден.

##### 3.2. Паттерн: Cache-Aside

**Чтение:** приложение само смотрит Redis → при miss идёт в MES DB → кладёт результат в Redis с TTL.

**Запись:** статус пишем **только в MES DB** (как сейчас + outbox). Кеш списка **не** обновляем Write-Through / Write-Behind — после записи делаем инвалидацию ключей.

| Паттерн | Почему не основной |
| --- | --- |
| **Read-Through** | Кеш сам ходит в БД; модель должна совпадать с БД; при сбое кеша сложнее fallback. Нам нужен контроль ключа и DTO в коде MES API. |
| **Refresh-Ahead** | Фоновый прогрев гоняет БД даже без читателей; список часто меняется — между тиками всё равно stale. Сложнее простого Cache-Aside. |
| **Write-Through** | Писать список целиком в кеш при каждой смене статуса неудобно (много ключей страниц/фильтров); проще удалить ключ. |
| **Write-Behind** | Для статуса заказа опасно: источник истины должен быть БД сразу, не «сначала кеш, БД потом». |

Cache-Aside: MES API уже знает, как собрать список; Redis только ускоряет повторные чтения.

##### 3.3. Sequence: чтение и запись

Сущности: **Оператор → MES UI → MES API → Redis / MES DB** (+ Rabbit при смене статуса).

| Сценарий | Диаграмма |
| --- | --- |
| Чтение списка (hit / miss) | [`c4/01-read-orders.puml`](c4/01-read-orders.puml) · [`c4/01-read-orders.svg`](c4/01-read-orders.svg) |
| Смена статуса + сброс кеша | [`c4/02-status-change.puml`](c4/02-status-change.puml) · [`c4/02-status-change.svg`](c4/02-status-change.svg) |

Кратко по шагам:

**Чтение**

1. UI запрашивает список у MES API.
2. API делает `GET` в Redis по ключу статуса/страницы.
3. Hit → отдаём клиенту.
4. Miss → запоминаем **текущую версию** `mes:orders:ver` → SELECT в MES DB → **условный SET** (только если версия не выросла) с TTL → отдаём клиенту.

**Запись статуса**

1. API обновляет заказ в MES DB (и outbox в той же транзакции — как в Task1).
2. API **атомарно** повышает `mes:orders:ver` (`INCR`) и сбрасывает ключи списков старого/нового статуса: `DEL` по известным ключам страниц или `SCAN` по префиксу `mes:orders:{status}:` — **не** `KEYS *` / `FLUSHALL`.
3. Публикация в Rabbit — как сейчас через outbox.
4. Следующий GET списка → miss → свежие данные; устаревший in-flight miss **не** перезапишет кеш.

##### 3.4. Инвалидация + версия кеша

Берём **комбинацию**:

| Способ | Как у нас | Роль |
| --- | --- | --- |
| **Версия списка + условный SET** | Ключ `mes:orders:ver`; miss читает `v` до SELECT; после commit статуса — `INCR` + `DEL`; перед заполнением — SET только если `ver == v` | Закрывает гонку «miss → старый SELECT → SET после DEL» |
| **По ключу + программная** | После смены статуса / «взять в работу» / появления заказа в MES — `DEL` известных ключей страниц (или `SCAN` по префиксу статуса) | Главный способ сброса снимка |
| **Временная (TTL)** | 30–60 с на ключ списка | Страховка, если забыли инвалидировать; ограничивает «вечный» stale |

**Гонка без версии.** Только `DEL` + TTL недостаточно:

1. Запрос A: cache miss → читает старый список из БД (заказ ещё «свободен»).
2. Запрос B: смена статуса → commit → `DEL` ключей.
3. Запрос A: `SET` устаревшего JSON **после** сброса.
4. Операторы снова видят занятый заказ как свободный — до минуты (TTL).

**Протокол версии** (как закрываем):

1. При промахе MES запоминает текущую версию в Redis **до** чтения из БД.
2. После коммита смены статуса MES атомарно повышает версию и удаляет затронутые ключи.
3. Перед заполнением кеша MES атомарно проверяет версию и делает `SET` только если она не изменилась (иначе отдаём свежий SELECT клиенту, но в Redis не кладём — следующий miss прочитает уже новую версию).

Атомарность шагов 2–3 — Lua-скрипт или `WATCH`/`MULTI` (или аналог в клиенте); не два независимых round-trip без проверки.

Почему не остальные **в одиночку**:

| Только так | Почему мало |
| --- | --- |
| Только TTL | До минуты заказ «свободен» у всех — плохо для гонки операторов |
| Только DEL без версии | In-flight miss после DEL снова кладёт stale список |
| Только по запросу без TTL | Если баг в коде инвалидации — кеш вечный |
| Только «на любое изменение в БД» без ключей | Сносить весь Redis при любом UPDATE — лишний thrashing |
| Только клиентский revalidate | Не чинит чужой браузер |

В проде для таких списков: **версия + event-driven delete + короткий TTL**.

Ключи: узкие (`status` + `page`) + один `mes:orders:ver`. Не кладём PII в значение кеша (те же правила, что в Task4).

#### 4. Дополнительно: сравнение вариантов (≥ 2)

Нужно выбрать одно. Ниже три рабочих варианта — с диаграммами, плюсами и минусами.

| | **Вариант 1 — берём** | **Вариант A** | **Вариант B** |
| --- | --- | --- | --- |
| Суть | Серверный **Cache-Aside** + Redis; запись в БД; **TTL + DEL + версия списка** | Клиентский **HTTP-кеш** (`Cache-Control: max-age`) на `GET /orders` | Серверный **Refresh-Ahead**: job периодически прогревает списки в Redis |
| Диаграмма | [чтение](c4/01-read-orders.puml) · [запись](c4/02-status-change.puml) | [`03-alt-http-client`](c4/03-alt-http-client.puml) | [`04-alt-refresh-ahead`](c4/04-alt-refresh-ahead.puml) |
| Плюсы | Общий снимок; Redis down → БД; сброс + условный SET закрывают stale после miss | Нет Redis; быстро внедрить заголовки | Почти всегда hit; низкая латентность на чтении |
| Минусы | Нужен Redis, ключи и дисциплина версии; секунды stale всё ещё возможны на самом SELECT | У каждого оператора свой кеш; сервер не сбросит чужой браузер → гонка за заказ | Job нагружает БД вхолостую; между тиками всё равно stale; сложнее сопровождать |
| Для «Александрита» | Да: дашборд общий, статусы часто меняются | Нет: ломает C1 (согласованность) | Можно как доп. прогрев позже, не как основу |

**Заключение:** берём **вариант 1** (Cache-Aside + DEL + **версия**). Закрывает боль операторов и гонку in-flight miss; совпадает с to-be Task1. Вариант A — нет (C1). Вариант B — опциональный прогрев позже.

Опционально позже (не в этом ADR): read-replica MES DB под miss — масштаб P2 из Task1, не вместо кеша.

### Альтернативы (кратко)

| Вариант                     | Почему нет сейчас                                      |
| --------------------------- | ------------------------------------------------------ |
| Кешировать всё MES API      | Узкое место — список дашборда                          |
| In-process memory без Redis | Два инстанса MES (P2) → разные кеши; нет общего сброса |
| Write-Behind статуса        | Риск потерять статус до записи в БД                    |
| CDN перед API списка        | Тот же класс проблем, что HTTP-кеш + лишняя точка      |

### Недостатки, ограничения, риски

| Риск | Что делаем |
| --- | --- |
| Stale список несколько секунд | Короткий TTL + DEL + bump версии; осознанный компромисс |
| In-flight miss пишет stale после DEL | Версия `mes:orders:ver` + условный SET (§3.4) |
| Забыли инвалидировать новый код-путь | TTL + code review + метрика hit/miss |
| Redis недоступен | Fallback на БД; алерт на Redis up (Task2) |
| Слишком широкие ключи / `KEYS *` / `FLUSHALL` | Только явные ключи страниц или `SCAN` по префиксу статуса |
| Кеш раздуется | TTL; не класть тяжёлые поля (3D и т.п.) |

### Последствия

**Лучше:** быстрее дашборд; меньше нагрузка на MES DB; операторы реже спорят из‑за устаревшего списка.

**Цена:** Redis в проде; дисциплина ключей и инвалидации в MES API.
